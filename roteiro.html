Semana 1

Python para produção

type hintsboto3pytestmotologging

O mercado quer Python de engenheiro de software: código organizado em camadas, testável e com logs úteis. Separe o handler (entrada da Lambda ou rota da API) da regra de negócio e do acesso a dados. Assim você testa a regra sem AWS.

handler.py · Lambda que salva um pedido no S3
# camadas: handler (entrada) -> service (regra) -> repo (AWS)
import json, logging, os
import boto3

log = logging.getLogger()
log.setLevel(logging.INFO)
s3 = boto3.client("s3")             # criado fora do handler: reaproveitado entre invocações
BUCKET = os.environ["BUCKET"]

def validar(pedido: dict) -> None:
    if pedido.get("valor", 0) <= 0:
        raise ValueError("valor deve ser positivo")

def salvar(pedido: dict) -> str:
    chave = f"bronze/pedidos/dt={pedido['data']}/{pedido['id']}.json"
    s3.put_object(Bucket=BUCKET, Key=chave, Body=json.dumps(pedido))
    return chave

def handler(event, context):
    pedido = json.loads(event["body"])
    try:
        validar(pedido)
    except ValueError as e:
        return {"statusCode": 400, "body": json.dumps({"erro": str(e)})}
    chave = salvar(pedido)
    log.info(json.dumps({"evento": "pedido_salvo", "id": pedido["id"], "chave": chave}))
    return {"statusCode": 201, "body": json.dumps({"chave": chave})}

Na entrevista

Como você estrutura um projeto Python para produção?

Em camadas (handler, serviço, repositório), configuração por variável de ambiente, dependências fixadas (pyproject.toml), lint com ruff, testes com pytest e mocks da AWS com moto, logs estruturados e tratamento de erro explícito.

Por que criar o client boto3 fora do handler?

O ambiente da Lambda é reaproveitado entre invocações (warm start). Criar o client fora do handler evita refazer a conexão a cada chamada, o que reduz latência e custo.

Semana 1

APIs e microsserviços

RESTFastAPIstatus codesidempotênciaresiliência

Uma API é um contrato: quem chama sabe o que mandar e o que vai receber. Em microsserviços, cada serviço tem seu próprio banco e se comunica de forma síncrona (HTTP, quando precisa da resposta na hora) ou assíncrona (eventos, para desacoplar).

main.py · API FastAPI com chave de idempotência
from fastapi import FastAPI, Header, HTTPException
from pydantic import BaseModel, Field

app = FastAPI(title="pedidos", version="1.0")
processados: dict[str, dict] = {}       # em produção: DynamoDB

class Pedido(BaseModel):
    cliente_id: str
    valor: float = Field(gt=0)          # validação automática, devolve 422 se inválido

@app.post("/v1/pedidos", status_code=201)
def criar(pedido: Pedido, idempotency_key: str = Header(...)):
    if idempotency_key in processados:  # cliente repetiu a chamada (timeout, retry)
        return processados[idempotency_key]
    resultado = {"id": idempotency_key, **pedido.model_dump(), "status": "criado"}
    processados[idempotency_key] = resultado
    return resultado

@app.get("/health")
def health():
    return {"ok": True}                 # usado pelo health check do ALB/ECS

Na entrevista

O que é idempotência e por que importa numa API?

Chamar a mesma operação várias vezes tem o mesmo efeito de chamar uma vez. Clientes refazem chamadas em timeout; sem idempotência você cobra o cliente duas vezes. A solução é uma chave única por operação, guardada e consultada antes de processar.

Monólito ou microsserviços?

Depende. Microsserviços dão deploy e escala independentes, mas cobram em rede, observabilidade e consistência distribuída. Para time pequeno ou domínio ainda instável, um monólito modular costuma ser melhor. Separe quando houver um motivo claro (escala, time, ciclo de deploy).

Como deixar a comunicação entre serviços resiliente?

Timeout em toda chamada, retry com backoff exponencial e jitter, circuit breaker para não derrubar quem depende, e eventos assíncronos onde a resposta imediata não é necessária.

Semana 2

AWS de aplicação: API Gateway, Lambda e ECS

API GatewayLambdaECS FargateALBECR

Há dois caminhos para rodar código: serverless (Lambda, você entrega uma função) e containers (ECS, você entrega uma imagem Docker). O ECS tem três conceitos: task definition (a receita: imagem, CPU, memória, variáveis), task (um container rodando) e service (mantém N tasks vivas atrás de um load balancer).

Na entrevista

Quando você escolhe Lambda e quando escolhe ECS?

Lambda para processamento por evento, curto e com carga irregular: paga só o que usa e escala sozinha. ECS para serviço sempre ligado, processos longos, tráfego constante (onde Lambda fica mais caro) ou quando preciso de controle do runtime.

REST API ou HTTP API no API Gateway?

HTTP API é mais barata e mais rápida, ideal para a maioria dos casos com JWT. REST API tem recursos extras: usage plans com API keys, validação de request, cache e integração direta com serviços AWS.

Como o ECS sabe que uma task está saudável?

Pelo health check do target group do ALB (por exemplo GET /health). Se falhar repetidamente, o ECS mata a task e sobe outra.

Semana 3

IAM e segurança

rolespoliciesmenor privilégioKMSSecrets Manager

Toda chamada na AWS responde à pergunta: quem (principal) pode fazer o quê (action) em qual recurso (resource). Serviços não usam usuários com chave fixa: eles assumem uma role e recebem credenciais temporárias.

policy.json · menor privilégio
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:PutObject"],
    "Resource": "arn:aws:s3:::meu-lake/bronze/pedidos/*"
  }]
}
  • Identity policy: anexada à role ou usuário (o que ele pode fazer).
  • Resource policy: anexada ao recurso, como uma bucket policy (quem pode acessá-lo). Necessária para acesso entre contas.
  • Segredos: senhas de banco ficam no Secrets Manager e nunca no código ou no repositório.
  • Criptografia: S3 e RDS com chave KMS; tráfego com TLS.

Na entrevista

Como uma task do ECS acessa o S3 sem chave de acesso?

Com uma task role. O ECS entrega credenciais temporárias ao container e o boto3 as encontra sozinho. A execution role é outra coisa: é usada pelo ECS para puxar a imagem do ECR e ler segredos.

Como dar acesso a um bucket para outra conta AWS?

Uma bucket policy permitindo o principal da outra conta e, na outra conta, uma policy na role permitindo a ação. As duas pontas precisam concordar. Outra opção é a outra conta assumir uma role na sua conta.

Semana 4 · maior peso

Eventos e arquitetura distribuída

SNSSQSEventBridgeKinesisDLQidempotência

Em vez de um sistema chamar o outro diretamente, ele publica um fato ("pedido criado") e quem tiver interesse consome. Isso desacopla times e absorve picos. A regra mais importante: a entrega é at-least-once, então uma mensagem pode chegar duas vezes e o consumidor precisa ser idempotente.

ServiçoModeloUse quando
SQSFila: cada mensagem é processada por um consumidor e someDistribuir trabalho, amortecer picos
SNSPub/sub: uma mensagem vai para vários assinantesFan-out para filas, e-mail, Lambda
EventBridgeBarramento com regras por conteúdo do eventoIntegração entre domínios, SaaS, agendamento
Kinesis / MSKStream ordenado, retido e relidoAlto volume, ordem por chave, vários leitores, replay
consumer.py · consumidor SQS idempotente com falha parcial do lote
import json, boto3
from botocore.exceptions import ClientError

tabela = boto3.resource("dynamodb").Table("eventos_processados")

def ja_processado(evento_id: str) -> bool:
    try:
        # grava só se o id ainda não existir (escrita condicional, atômica)
        tabela.put_item(Item={"id": evento_id},
                        ConditionExpression="attribute_not_exists(id)")
        return False
    except ClientError as e:
        if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
            return True
        raise

def handler(event, context):
    falhas = []
    for record in event["Records"]:
        try:
            msg = json.loads(record["body"])
            if ja_processado(msg["evento_id"]):
                continue                     # duplicata: ignora sem erro
            faturar(msg)
        except Exception:
            falhas.append({"itemIdentifier": record["messageId"]})
    # só as mensagens com erro voltam para a fila (ReportBatchItemFailures)
    return {"batchItemFailures": falhas}

Atenção: nesse exemplo, se faturar falhar depois do registro, o retry vai achar o id e pular. Em produção, marque como processado só depois do sucesso, ou use status (EM_ANDAMENTO → OK) com expiração. Mencionar esse detalhe na entrevista mostra maturidade.

Padrões que você precisa conhecer

  • Outbox: grava o dado e o evento na mesma transação do banco; um processo separado publica o evento. Evita o caso "salvou no banco, mas não publicou".
  • Saga: transação distribuída em passos, cada passo com uma ação de compensação (cancelar reserva se o pagamento falhar). Step Functions orquestra bem.
  • CQRS: modelo de escrita separado do modelo de leitura, sincronizados por eventos.
  • Consistência eventual: os sistemas convergem depois de um tempo, não no mesmo instante.

Na entrevista

Como evitar processar o mesmo evento duas vezes?

Cada evento tem um id único. O consumidor registra o id no DynamoDB com escrita condicional (attribute_not_exists). Se a escrita falhar por condição, é duplicata e ele ignora. Também é possível desenhar a operação para ser naturalmente idempotente (um upsert em vez de um insert).

O que é visibility timeout no SQS?

Quando um consumidor lê a mensagem, ela fica invisível por esse tempo. Se ele não apagar a mensagem a tempo, ela volta para a fila. Deve ser maior que o tempo de processamento (na Lambda, recomenda-se 6x o timeout da função).

Quando a ordem das mensagens importa, o que você usa?

SQS FIFO com MessageGroupId (ordem por grupo, por exemplo por cliente) ou Kinesis com partition key. Ordem global costuma ser desnecessária e cara; ordem por entidade basta.

Semana 5

Bancos relacionais e NoSQL

Postgres / RDSSQL avançadoDynamoDBmodelagem

Relacional quando os dados têm relações e você não sabe todas as consultas de antemão. NoSQL (DynamoDB) quando você conhece os padrões de acesso e precisa de escala e latência previsível. No DynamoDB, você modela a partir das perguntas, não das entidades.

SQL · window functions e CTE (cai muito em teste técnico)
-- último pedido de cada cliente e variação em relação ao anterior
WITH ordenados AS (
  SELECT cliente_id, pedido_id, valor, criado_em,
         ROW_NUMBER() OVER (PARTITION BY cliente_id ORDER BY criado_em DESC) AS rn,
         LAG(valor)   OVER (PARTITION BY cliente_id ORDER BY criado_em)      AS valor_anterior
  FROM pedidos
)
SELECT cliente_id, pedido_id, valor, valor - valor_anterior AS variacao
FROM ordenados
WHERE rn = 1;
Python · consulta no DynamoDB pela chave
from boto3.dynamodb.conditions import Key
resp = tabela.query(
    KeyConditionExpression=Key("PK").eq("CLIENTE#42") & Key("SK").begins_with("PEDIDO#"),
    ScanIndexForward=False,   # mais recentes primeiro
    Limit=10,
)

Na entrevista

Por que evitar Scan no DynamoDB?

O Scan lê a tabela inteira e cobra por tudo que leu. Use Query por partition key ou crie um GSI para o padrão de acesso que falta.

Uma query no Postgres está lenta. O que você faz?

Rodo EXPLAIN ANALYZE, procuro seq scan em tabela grande, crio índice nas colunas de filtro e join, reviso SELECT *, verifico estatísticas (ANALYZE) e, se for leitura pesada, considero réplica de leitura ou view materializada.

Semana 6

Dados: S3, Glue, EMR e Athena

medallionParquetIcebergPySparkparticionamento

O data lake no S3 é organizado em camadas. Bronze guarda o dado bruto como chegou (permite reprocessar). Silver é limpo, tipado e sem duplicatas. Gold traz as tabelas de negócio prontas para consumo. O Glue Data Catalog guarda os schemas; o Athena consulta com SQL.

job_silver.py · Glue / EMR em PySpark
from pyspark.sql import SparkSession, functions as F, Window

spark = SparkSession.builder.getOrCreate()
bruto = spark.read.json("s3://lake/bronze/pedidos/dt=2026-11-10/")

# dedup: fica a versão mais recente de cada pedido
w = Window.partitionBy("id").orderBy(F.col("atualizado_em").desc())
silver = (bruto
    .withColumn("valor", F.col("valor").cast("decimal(12,2)"))
    .filter(F.col("valor") > 0)
    .withColumn("rn", F.row_number().over(w)).filter("rn = 1").drop("rn")
    .withColumn("dt", F.to_date("criado_em")))

(silver.write.mode("overwrite")
    .partitionBy("dt")
    .parquet("s3://lake/silver/pedidos/"))
Athena · consulta que lê só uma partição
SELECT cliente_id, SUM(valor) AS total
FROM silver.pedidos
WHERE dt = DATE '2026-11-10'      -- filtro na partição: lê pouco, paga pouco
GROUP BY cliente_id;

Na entrevista

O que é o problema dos arquivos pequenos e como resolver?

Milhares de arquivos de poucos KB deixam Spark e Athena lentos (abrir arquivo custa mais que ler). Resolva com coalesce ou repartition antes de gravar, buffer maior no Firehose e compactação periódica (no Iceberg, OPTIMIZE ou rewrite_data_files). O alvo é arquivos de 128 MB a 1 GB.

Como tornar um pipeline idempotente?

Reprocessar a mesma data deve dar o mesmo resultado: sobrescrever a partição (overwrite dinâmico) ou fazer MERGE por chave no Iceberg, nunca apenas append cego.

Semana 7

Git, CI/CD e Terraform

GitGitHub ActionsTerraformOIDCdeploy

Nada vai para produção pela mão. O código passa pela esteira: testes, build, plano de infraestrutura revisado no pull request e deploy automático. A infraestrutura também é código (Terraform), versionada no Git, então dá para revisar, repetir e desfazer.

.github/workflows/deploy.yml
name: deploy
on:
  push: { branches: [main] }
  pull_request:
permissions:
  id-token: write        # necessário para OIDC
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt ruff pytest
      - run: ruff check . && pytest -q
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: producao  # exige aprovação manual configurada no GitHub
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-deploy
          aws-region: us-east-1
      - uses: hashicorp/setup-terraform@v3
      - run: terraform -chdir=infra init && terraform -chdir=infra apply -auto-approve

Na entrevista

Descreva uma esteira ideal para um microsserviço.

No PR: lint, testes, build da imagem e terraform plan comentado no PR. No merge: push da imagem com tag do commit, deploy automático em dev, testes de fumaça, aprovação e deploy canary em produção, com rollback automático se os alarmes dispararem.

Por que OIDC em vez de access key no GitHub?

A access key é permanente e vaza. Com OIDC, o GitHub recebe credenciais temporárias de uma role que só confia naquele repositório e branch.

Semana 8 · diferencial

Observabilidade, DataOps e produção

Observabilidade é conseguir responder "o que está acontecendo e por quê" sem fazer deploy de código novo. São três pilares: logs (o que aconteceu), métricas (quanto e com que frequência) e traces (o caminho de uma requisição entre serviços).

  • SLI / SLO / SLA: SLI é a medida (99,2% das requisições abaixo de 300 ms), SLO é a meta interna (99,5%), SLA é o compromisso com o cliente, com penalidade.
  • DataOps: testes de qualidade no pipeline (Glue Data Quality ou Great Expectations), contratos de dados entre produtor e consumidor, linhagem e versionamento.
  • Operação: runbook para cada alarme, post-mortem sem culpados, revisão de custo mensal.

Na entrevista

Um pipeline falhou às 3h da manhã. O que você faz?

O alarme dispara e eu sigo o runbook: vejo os logs e o trace para achar a causa, corrijo ou contorno, reprocesso a partir da camada bronze (que é imutável) com um job idempotente, confirmo a qualidade do resultado, aviso os consumidores e depois escrevo o post-mortem com ações para não repetir.

Como você saberia que os dados estão errados antes do usuário perceber?

Checagens automáticas no pipeline: volume de linhas fora do esperado, nulos em colunas obrigatórias, chaves duplicadas, valores fora do intervalo e atraso da partição. Uma falha bloqueia a publicação na gold e dispara alarme.
