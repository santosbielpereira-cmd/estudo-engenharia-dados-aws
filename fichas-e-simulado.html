Parte 1

Spark: arquitetura

Antes de otimizar qualquer coisa, entenda quem faz o quê quando você roda um job.

Driver Program, Cluster Manager e Executors

Situação: você roda spark-submit job.py. O que acontece por baixo, e por que nessa ordem?

Driver

O "cérebro". É o processo que roda o seu main e cria a SparkSession. Transforma o código num plano (DAG), quebra em stages e tasks, distribui as tasks e junta os resultados. Existe um por aplicação.

Cluster Manager

O "RH do cluster". Não processa dado nenhum. Sabe quais máquinas têm CPU e memória livres e entrega recursos para o Driver. No EMR é o YARN; no Kubernetes é o próprio K8s; no Glue a AWS esconde isso de você.

Executors

Os "braços". Processos JVM nas máquinas workers que executam as tasks, guardam dados em cache e gravam o shuffle. Cada executor tem N cores, e cada core roda uma task por vez.

Por que nessa ordem

  1. O Driver nasce primeiro porque é ele que sabe o que precisa ser feito e quantos recursos pedir.
  2. O Driver pede ao Cluster Manager, porque só ele sabe onde há recursos livres. O Spark não quer reinventar o gerenciamento de máquinas.
  3. O Cluster Manager sobe os Executors nos workers, que se registram no Driver.
  4. A partir daí o Driver manda tasks direto aos Executors, sem intermediário, o que evita gargalo.

Como usar

spark-submit \
  --deploy-mode cluster \          # driver roda dentro do cluster (produção)
  --num-executors 10 \
  --executor-cores 4 \             # 4 tasks em paralelo por executor
  --executor-memory 16g \
  --driver-memory 4g \
  job.py
# paralelismo total = 10 executors x 4 cores = 40 tasks ao mesmo tempo

Cuidado

  • collect() traz todos os dados para o Driver. Com tabela grande, o Driver morre por falta de memória. Use show(), take(n) ou grave no S3.
  • --deploy-mode client deixa o Driver na sua máquina: se ela desconectar, o job morre. Em produção use cluster.
  • Executor com cores demais (mais de 5) costuma piorar a vazão de I/O com o HDFS/S3. O padrão comum é 4 ou 5.
Na entrevista: "O que acontece se um executor morrer no meio do job?"

O Driver percebe pela falta de heartbeat, pede outro executor ao Cluster Manager e reexecuta só as tasks perdidas. Ele consegue porque guarda a linhagem (lineage) de como cada partição foi calculada. Se o Driver morrer, a aplicação inteira falha, porque ele é o único que conhece o plano.

Job, Stage e Task

Situação: você abre o Spark UI e vê "Job 3, Stage 7, 200 tasks". O que é cada coisa?

Job

Disparado por cada action: count(), write, collect(), show(). Três actions no código geram três jobs.

Stage

Um trecho do job que roda sem precisar trocar dados entre máquinas. Todo shuffle cria uma fronteira e começa um stage novo.

Task

A menor unidade de trabalho: um stage aplicado a uma partição. 200 partições geram 200 tasks. Cada task ocupa um core.

Por que dividir assim

Dentro de um stage, o Spark encadeia as operações em sequência sobre a mesma partição (pipelining), sem gravar nada no meio. Isso é rápido. Só quando os dados precisam mudar de máquina (shuffle) ele é obrigado a parar, gravar em disco e começar outro stage.

Na entrevista: "Um stage tem 200 tasks; 199 terminam em 10 s e uma leva 20 min. O que é?"

Data skew: uma partição tem muito mais dados que as outras (uma chave concentra a maioria das linhas). A solução está nas fichas de skew e AQE.

Lazy evaluation e DAG

Situação: você roda 10 linhas de transformação e nada acontece. Quando chega no .write, o job demora. Por quê?

O que é

Transformações (filter, select, join, groupBy) não executam nada: só anotam no plano. Actions (write, count, collect) disparam a execução. O plano é um DAG (grafo de passos sem ciclos).

Por que funciona

Vendo o plano inteiro antes de rodar, o otimizador Catalyst reordena e corta trabalho: empurra filtros para a leitura, lê só as colunas usadas e escolhe a estratégia de join. Se executasse linha a linha, não teria como otimizar.

df = spark.read.parquet("s3://lake/silver/pedidos/")
df2 = df.filter("dt = '2026-11-10'").select("cliente_id", "valor")   # nada roda ainda
df2.explain(True)   # mostra o plano: veja PushedFilters e as colunas lidas
df2.write.parquet("s3://lake/gold/x/")                              # agora roda

Cuidado

Se você usa o mesmo DataFrame em duas actions, o Spark recalcula tudo duas vezes, desde a leitura. Para evitar, use cache() (ficha 10).

Na entrevista: "Diferença entre transformação narrow e wide?"

Narrow: cada partição de saída depende de uma só partição de entrada (filter, map, select), não move dados. Wide: precisa de dados de várias partições (groupBy, join, distinct, orderBy), gera shuffle e um novo stage.

Spark: DataFrame e agrupamento

A API que você mais vai usar no dia a dia, e o que acontece por baixo de cada linha.

RDD, DataFrame e Dataset

Situação: o entrevistador pergunta "qual a diferença entre RDD e DataFrame, e por que hoje quase ninguém usa RDD?"

RDDDataFrameDataset
O que éColeção distribuída de objetosTabela distribuída com colunas nomeadas e schemaDataFrame com tipo forte (só Scala/Java)
SchemaNão tem: o Spark não sabe o que há dentroTem: nomes e tipos de colunasTem, checado na compilação
OtimizaçãoNenhuma: roda exatamente o que você escreveuCatalyst + TungstenCatalyst + Tungsten

Por que o DataFrame ganhou

Com o RDD, o Spark recebe uma função "caixa-preta" e não sabe o que ela faz, então não consegue otimizar nada. Com o DataFrame, você declara o quê quer (filtrar, agrupar, somar) e o Spark, conhecendo o schema, decide como fazer: lê só as colunas usadas, empurra filtros para a leitura e escolhe o melhor join. É a mesma ideia do SQL num banco.

# RDD: você descreve o "como", em Python, linha a linha
rdd.map(lambda r: (r["loja"], r["valor"])).reduceByKey(lambda a, b: a + b)

# DataFrame: você descreve o "o quê"; o Spark otimiza
df.groupBy("loja").agg(F.sum("valor"))

# Spark SQL: gera exatamente o mesmo plano que o DataFrame acima
df.createOrReplaceTempView("vendas")
spark.sql("SELECT loja, SUM(valor) FROM vendas GROUP BY loja")
Na entrevista: "Spark SQL é mais rápido que a API de DataFrame?"

Não. Os dois passam pelo mesmo otimizador (Catalyst) e geram o mesmo plano físico. A escolha é de legibilidade e de time: SQL para quem vem de banco, a API para lógica composta em Python, com funções e testes.

Operações essenciais do DataFrame

Situação: teste técnico: "leia esses pedidos, limpe, calcule o total por cliente e grave em Parquet".

from pyspark.sql import SparkSession, functions as F, types as T

spark = SparkSession.builder.appName("pedidos").getOrCreate()

schema = T.StructType([
    T.StructField("id", T.StringType()),
    T.StructField("cliente_id", T.StringType()),
    T.StructField("valor", T.DecimalType(12, 2)),
    T.StructField("status", T.StringType()),
    T.StructField("criado_em", T.TimestampType()),
])
df = spark.read.schema(schema).json("s3://lake/bronze/pedidos/")    # schema explícito: sem inferência

limpo = (df
    .filter(F.col("status") != "cancelado")                       # linhas
    .select("id", "cliente_id", "valor", "criado_em")             # colunas
    .withColumn("dt", F.to_date("criado_em"))                     # coluna nova
    .withColumn("faixa", F.when(F.col("valor") >= 1000, "alto")
                          .when(F.col("valor") >= 100, "medio")
                          .otherwise("baixo"))
    .withColumnRenamed("cliente_id", "cliente")
    .dropDuplicates(["id"])
    .na.fill({"faixa": "desconhecida"}))

total = limpo.groupBy("cliente").agg(F.sum("valor").alias("total"))
total.orderBy(F.desc("total")).show(10)
total.write.mode("overwrite").parquet("s3://lake/gold/total_por_cliente/")

Cuidado

  • Encadear dezenas de withColumn num laço cria um plano enorme e lento de compilar. Para muitas colunas, use um único select com uma lista de expressões.
  • union junta por posição das colunas; se a ordem difere, os dados se misturam sem erro. Prefira unionByName.
  • show() e count() são actions: cada uma roda o plano inteiro.

Catalyst e Tungsten: por que o DataFrame é rápido

Situação: você escreveu o filtro depois do join, mas no explain() o filtro aparece antes. Quem mudou?

Catalyst (o otimizador)

  • Predicate pushdown: move filtros para o mais cedo possível.
  • Column pruning: remove colunas que ninguém usa.
  • Constant folding: calcula 1 + 1 uma vez só.
  • Escolhe a estratégia de join (broadcast, sort-merge).

Tungsten (o motor)

  • Guarda os dados em formato binário compacto, fora dos objetos Java, o que reduz o uso de memória e o trabalho do garbage collector.
  • Whole-stage codegen: junta várias operações num único laço de código compilado. No plano, aparece como *(1) antes do operador.
df.explain("formatted")   # mostra o plano físico, PushedFilters, colunas lidas e a estratégia de join

groupBy e agg por dentro

Situação: "Por que um groupBy com sum sobre 1 bilhão de linhas é rápido, mas um collect_list no mesmo groupBy estoura a memória?"

O que acontece

O Spark divide a agregação em duas fases. Na parcial, cada task soma localmente as linhas da sua partição. Só esse resumo passa pelo shuffle. Na final, cada partição recebe os resumos de uma chave e combina. No explain() aparecem dois HashAggregate com um Exchange no meio.

Por que sum escala e collect_list não

sum, count, min, max e avg têm um resumo de tamanho fixo (um número, ou soma e contagem no caso da média), então a fase parcial reduz muito o volume. O collect_list precisa guardar todos os valores de cada chave, então o resumo é do tamanho do dado. Com uma chave grande, a lista inteira precisa caber na memória de uma task.

resumo = (vendas
    .groupBy("loja_id", "dt")
    .agg(
        F.count("*").alias("qtd"),
        F.sum("valor").alias("receita"),
        F.avg("valor").alias("ticket_medio"),
        F.countDistinct("cliente_id").alias("clientes"),          # exato, mais caro
        F.approx_count_distinct("cliente_id").alias("clientes_aprox"),  # ~2% de erro, muito mais barato
        F.sum(F.when(F.col("status") == "pago", F.col("valor"))).alias("receita_paga"),  # agregação condicional
    ))

# pivot: transforma valores em colunas; informe a lista para evitar um job extra
vendas.groupBy("loja_id").pivot("canal", ["site", "app", "loja"]).sum("valor")

# subtotais por nível (equivale a GROUPING SETS)
vendas.rollup("regiao", "loja_id").agg(F.sum("valor"))

Cuidado

  • Agrupar por uma chave com skew concentra a fase final numa task só. A fase parcial ajuda, mas não resolve totalmente: veja a ficha de skew.
  • Em groupBy, linhas com chave NULL formam um grupo próprio. Se a coluna tem muitos nulos, vira uma chave quente.
  • pivot sem a lista de valores roda um job extra só para descobrir os valores distintos.
Na entrevista: "Como você calcula o total de vendas por loja num dataset de 5 TB?"

Leio só as colunas loja_id e valor (o Parquet ajuda), filtro as partições de data necessárias e faço groupBy("loja_id").agg(sum("valor")). O Spark agrega parcialmente em cada partição, então o shuffle é pequeno. Se uma loja dominar, o AQE ou salting resolvem a fase final.

groupBy ou window function

Situação: você precisa do total por cliente, mas sem perder as linhas de cada pedido. Com groupBy as linhas somem.

groupBy

Colapsa as linhas: um resultado por grupo. 1 milhão de pedidos de 1.000 clientes viram 1.000 linhas.

Window

Mantém todas as linhas e acrescenta uma coluna calculada sobre um grupo (a "janela"). 1 milhão de pedidos continuam 1 milhão, agora com o total do cliente ao lado.

from pyspark.sql import Window

por_cliente = Window.partitionBy("cliente_id")
ordenado = por_cliente.orderBy("criado_em")

resultado = (pedidos
    .withColumn("total_cliente", F.sum("valor").over(por_cliente))
    .withColumn("pct_do_total", F.col("valor") / F.col("total_cliente"))
    .withColumn("n_pedido", F.row_number().over(ordenado))              # 1, 2, 3...
    .withColumn("valor_anterior", F.lag("valor").over(ordenado))        # linha anterior
    .withColumn("acumulado", F.sum("valor").over(
        ordenado.rowsBetween(Window.unboundedPreceding, Window.currentRow)))  # soma corrente
    .withColumn("media_movel_3", F.avg("valor").over(ordenado.rowsBetween(-2, 0))))

# padrão clássico: o registro mais recente de cada chave (dedup)
mais_recente = (clientes
    .withColumn("rn", F.row_number().over(Window.partitionBy("id").orderBy(F.desc("atualizado_em"))))
    .filter("rn = 1").drop("rn"))
FunçãoO que fazEmpate
row_numberNumera 1, 2, 3...Desempata de forma arbitrária
rank1, 2, 2, 4Pula posições após empate
dense_rank1, 2, 2, 3Não pula posições
lag / leadValor da linha anterior / seguinte-

Cuidado

  • A window precisa juntar todas as linhas de cada partição de janela numa task e ordená-las. Uma window sem partitionBy joga a tabela inteira numa única task.
  • Se o que você quer é só o total por grupo, sem as linhas, groupBy é mais barato, porque ele agrega parcialmente e a window não.
  • Com orderBy e sem frame explícito, a soma vira acumulada por padrão (rangeBetween(unboundedPreceding, currentRow)). Isso surpreende muita gente.

Schema, tipos e nulos

Situação: o job lê JSON com inferSchema, demora para começar, e um dia a coluna valor vira string e quebra o pipeline.

Por que definir o schema

  • Desempenho: inferir o schema obriga o Spark a ler os dados uma vez a mais antes de começar.
  • Estabilidade: um arquivo com "valor": "N/A" muda o tipo inferido da coluna inteira.
  • Contrato: o schema documenta o que o pipeline espera receber.

Modos de leitura para dado ruim

  • PERMISSIVE (padrão): campos inválidos viram nulo; a linha original vai para _corrupt_record.
  • DROPMALFORMED: descarta a linha em silêncio. Perigoso.
  • FAILFAST: falha no primeiro erro. Bom para dados que precisam ser perfeitos.
df = (spark.read.schema(schema)
      .option("mode", "PERMISSIVE")
      .option("columnNameOfCorruptRecord", "_corrupt_record")
      .json("s3://lake/bronze/pedidos/"))
# ruins para uma tabela de quarentena, bons seguem; não perde dado nem quebra o job
ruins = df.filter(F.col("_corrupt_record").isNotNull())

Nulos que pegam de surpresa

  • NULL = NULL não é verdadeiro: é nulo. Por isso chaves nulas nunca casam num join. Para casar nulos, use eqNullSafe (<=> em SQL).
  • count("coluna") ignora nulos; count("*") conta todas as linhas.
  • avg ignora nulos: a média de [10, NULL, 20] é 15, e não 10.
  • filter(col("status") != "cancelado") também descarta as linhas com status nulo.
  • Use decimal para dinheiro, nunca double: 0.1 + 0.2 em double dá 0.30000000000000004.

Dedup e count distinct

Situação: o mesmo evento chegou três vezes (entrega at-least-once) e o relatório mostra receita triplicada.

MétodoQuando usarCusto

Por que dropDuplicates pode ser perigoso

Ele mantém "alguma" cópia, e qual delas depende da ordem em que os dados chegaram às partições. Se as cópias diferem (por exemplo, status novo e pago), duas execuções podem dar resultados diferentes. Quando a versão importa, use row_number com uma ordenação explícita.

Na entrevista: "Como você deduplica um stream?"

No Structured Streaming, withWatermark("evento_ts", "1 hour").dropDuplicates(["evento_id", "evento_ts"]). A watermark diz por quanto tempo o Spark guarda os ids já vistos; sem ela, esse estado cresceria para sempre. Fora do Spark, a mesma ideia vale: guardar o id processado no DynamoDB com expiração (TTL).

Parte 2

Spark: performance

Quase todo problema de performance em Spark é um destes: shuffle demais, partições erradas, join mal escolhido, skew ou memória.

Shuffle: a operação mais cara do Spark

Situação: o job passa a maior parte do tempo em "Shuffle Read / Shuffle Write" no Spark UI.

O que é

Redistribuir os dados entre executores para que linhas com a mesma chave fiquem juntas. Necessário para groupBy, join, distinct, orderBy e repartition.

Por que é caro

Envolve três custos de uma vez: serialização (converter objetos em bytes), disco (cada executor grava arquivos de shuffle) e rede (todos mandam para todos). CPU é barata; rede e disco não.

Como reduzir

  • Filtre e selecione colunas antes do join ou groupBy: menos bytes para mover.
  • Use broadcast join quando um lado for pequeno: elimina o shuffle do lado grande.
  • Ajuste spark.sql.shuffle.partitions (padrão 200) ao volume, ou deixe o AQE ajustar.
  • Evite orderBy global se não precisar; um sort dentro da partição é mais barato.
Na entrevista: "Por que reduceByKey é melhor que groupByKey em RDD?"

O reduceByKey faz uma agregação parcial em cada partição antes do shuffle (map-side combine), então envia um valor por chave por partição. O groupByKey envia todas as linhas pela rede. Em DataFrames, o groupBy().agg() já faz a agregação parcial automaticamente.

Partições: repartition e coalesce

Situação: o job grava 5.000 arquivos minúsculos no S3, ou só usa 2 dos 40 cores disponíveis.

O que é uma partição

Um pedaço do DataFrame processado por uma task. O número de partições define o paralelismo: com 2 partições, só 2 cores trabalham, mesmo com 40 livres. Regra prática: partições de 100 a 200 MB, e de 2 a 4 vezes o número de cores.

Comparação

repartition(n)coalesce(n)
DireçãoAumenta ou diminuiSó diminui
ShuffleSim (completo)Não (junta partições vizinhas)
ResultadoPartições balanceadasPodem ficar desiguais

Por que coalesce é mais barato

O coalesce só junta partições que já estão no mesmo executor, sem mover dados pela rede. O repartition embaralha tudo para balancear, o que exige shuffle. Para reduzir arquivos antes de gravar, prefira coalesce, desde que as partições de entrada não sejam muito desiguais.

df.groupBy(F.spark_partition_id().alias("p")).count().orderBy("p").show()

Três confusões clássicas

  • Partição em memória e partição em disco são coisas diferentes. repartition e coalesce mudam os pedaços em memória que viram tasks. write.partitionBy("dt") cria pastas no S3 (dt=2026-11-10/) e serve para pular dados na leitura. Uma não substitui a outra.
  • F.coalesce é outra função. Em SQL e em pyspark.sql.functions, coalesce(a, b, 0) devolve o primeiro valor não nulo. Não tem nada a ver com partições. É pegadinha comum.
  • O coalesce afeta o stage inteiro. Como não há shuffle para criar uma fronteira, o Spark aplica o número menor de partições a tudo que vem antes no mesmo stage. Um filter pesado seguido de coalesce(1) roda o filtro numa task só. Nesse caso, repartition(1) é mais rápido, porque o filtro continua paralelo e só a escrita é única.
Na entrevista: "Qual a diferença entre repartition e coalesce, e quando você usa cada um?"

repartition faz shuffle completo, aumenta ou diminui e deixa as partições balanceadas; uso para ganhar paralelismo, corrigir partições desiguais ou distribuir por uma chave. coalesce só diminui e junta partições sem shuffle, então é mais barato; uso para reduzir arquivos na escrita. O cuidado é que o coalesce reduz o paralelismo do stage inteiro, então com um valor muito baixo pode ser mais lento que o repartition.

Broadcast join

Situação: o join entre vendas (2 bilhões de linhas) e lojas (500 linhas) está lento.

O que é

Uma estratégia de join em que a tabela pequena é copiada inteira para a memória de todos os executores. Cada executor faz o join localmente com o pedaço da tabela grande que já tem.

Por que funciona

Num join normal, as duas tabelas são embaralhadas para que chaves iguais se encontrem na mesma máquina. Se uma tabela tem 500 linhas, é muito mais barato mandar uma cópia dela para cada executor do que mover 2 bilhões de linhas pela rede. Você troca um shuffle enorme por uma cópia pequena.

Como usar

from pyspark.sql.functions import broadcast

resultado = vendas.join(broadcast(lojas), "loja_id")   # força o broadcast

# ou deixe automático: o Spark faz broadcast de tabelas abaixo deste limite (padrão 10 MB)
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", 50 * 1024 * 1024)   # 50 MB

# em SQL
spark.sql("SELECT /*+ BROADCAST(l) */ * FROM vendas v JOIN lojas l ON v.loja_id = l.loja_id")

resultado.explain()   # confirme: deve aparecer BroadcastHashJoin

Cuidado

  • A tabela pequena precisa caber na memória do Driver (que a coleta primeiro) e de cada executor. Fazer broadcast de 2 GB derruba o job com OOM.
  • Não funciona como lado "preservado" de alguns outer joins: em vendas LEFT JOIN lojas, só lojas pode ser o lado broadcast.
  • O tamanho estimado pelo Spark pode estar errado depois de filtros; confira com explain().
Na entrevista: "Seu join está lento. Como você investiga?"

Abro o Spark UI e vejo qual stage demora e se há shuffle grande ou skew. Rodo explain() para ver a estratégia de join. Se um lado for pequeno (até algumas centenas de MB), aplico broadcast. Se os dois forem grandes, filtro e seleciono colunas antes, confiro se o tamanho das partições está bom e trato skew com AQE ou salting. Por último, avalio pré-particionar ou usar bucketing se o join se repete todo dia.

Estratégias de join do Spark

Situação: no explain() aparece SortMergeJoin. O que isso significa e quais são as alternativas?

EstratégiaComo funcionaQuando o Spark escolheCusto
Broadcast Hash JoinCopia o lado pequeno para todos e monta uma tabela hash em memóriaUm lado abaixo do limite de broadcastO mais rápido, sem shuffle
Shuffle Hash JoinShuffle nos dois lados; em cada partição, monta hash do lado menorUm lado bem menor que o outro, mas grande para broadcastUm shuffle, sem ordenação
Sort-Merge JoinShuffle nos dois lados, ordena pela chave e percorre os dois em paraleloPadrão para duas tabelas grandesShuffle e sort, mas escala e pode gravar em disco

CartesianTodas as combinaçõescrossJoin ou join sem condiçãoN × M linhas: quase sempre erro

Por que o sort-merge é o padrão

Ele não precisa que nenhum lado caiba na memória: depois de ordenar, basta percorrer os dois lados como num zíper, e se a memória acabar ele grava em disco (spill). É mais lento que um hash join, mas não quebra com volume grande.

Na entrevista: "Por que join com BETWEEN é lento?"

Sem igualdade na condição, o Spark não consegue usar hash nem ordenar pela chave, então cai no nested loop (compara tudo com tudo). A saída é criar uma chave de igualdade, por exemplo arredondar a data para o dia ("bucket" de intervalo), fazer o join por ela e só depois aplicar o filtro exato.

Data skew e salting

Situação: 199 tasks terminam em segundos e uma leva 30 minutos. O cliente "AMAZON" tem 40% das linhas.

O que é

Distribuição desigual: o shuffle manda todas as linhas de uma chave para a mesma partição. Se uma chave domina, uma task recebe quase tudo, e o stage inteiro espera por ela.

Por que o salting funciona

Você adiciona um número aleatório à chave ("sal"), transformando uma chave quente em N chaves diferentes, que vão para N partições. Do outro lado do join, você replica cada linha N vezes, uma para cada sal, para que os pares continuem se encontrando.

from pyspark.sql import functions as F
N = 8

# lado grande: sal aleatório de 0 a N-1
vendas_s = vendas.withColumn("sal", (F.rand() * N).cast("int"))

# lado menor: replica cada linha N vezes, uma por sal
clientes_s = clientes.withColumn("sal", F.explode(F.array([F.lit(i) for i in range(N)])))

resultado = vendas_s.join(clientes_s, ["cliente_id", "sal"]).drop("sal")

Cuidado

  • O lado replicado cresce N vezes. Aplique o sal só às chaves quentes se possível.
  • Antes de salting manual, ative o AQE: no Spark 3 ele resolve boa parte do skew sozinho.
  • Se a chave quente for NULL, o problema pode ser outro: filtre os nulos antes do join, já que eles nunca casam.
Na entrevista: "Como você detecta skew?"

No Spark UI, na aba do stage, comparo a duração e o "Shuffle Read Size" das tasks: se o máximo é muito maior que a mediana, há skew. No código, um groupBy("chave").count().orderBy(desc("count")) mostra as chaves quentes.

AQE: Adaptive Query Execution

Situação: você não sabe o tamanho certo de shuffle.partitions, e o volume muda todo dia.

O que é

Desde o Spark 3, o plano pode ser reajustado durante a execução, com base no tamanho real dos dados depois de cada shuffle, e não só nas estimativas feitas antes de começar.

Por que funciona

O otimizador clássico decide tudo antes de rodar, com estatísticas que muitas vezes estão erradas. O AQE espera cada stage terminar, mede o resultado e então decide o próximo passo com números reais.

O que o AQE fazConfiguração
Junta partições pequenas depois do shuffle (evita 200 tasks de 1 MB)spark.sql.adaptive.coalescePartitions.enabled
Troca sort-merge por broadcast se um lado ficou pequeno após filtrosautomático com AQE ligado
Divide partições com skew em várias tasksspark.sql.adaptive.skewJoin.enabled
spark.conf.set("spark.sql.adaptive.enabled", "true")            # padrão desde o Spark 3.2
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
Na entrevista: "O AQE substitui o broadcast manual?"

Em parte. Ele converte para broadcast quando descobre em tempo de execução que um lado é pequeno, mas só depois de rodar o stage anterior. Se você já sabe que a tabela é pequena, o hint broadcast() evita até o primeiro shuffle.

Cache e persist

Situação: você usa o mesmo DataFrame limpo em três agregações diferentes e o job lê o S3 três vezes.

O que é

Guardar o resultado de um DataFrame na memória (ou disco) dos executores para reaproveitar em várias actions. cache() é atalho para persist(MEMORY_AND_DISK) em DataFrames.

Por que funciona

Por causa da lazy evaluation, cada action recalcula o DataFrame desde a origem. O cache "corta" a linhagem: a partir dali, as próximas actions partem do dado já calculado.

from pyspark import StorageLevel
limpo = bruto.filter(...).dropDuplicates(["id"]).persist(StorageLevel.MEMORY_AND_DISK)
limpo.count()                 # action que materializa o cache
por_dia    = limpo.groupBy("dt").sum("valor")
por_regiao = limpo.groupBy("regiao").sum("valor")
limpo.unpersist()             # libera a memória quando terminar

Cuidado

Cache ocupa memória que o shuffle e os joins também precisam. Fazer cache de tudo "por garantia" causa spill e piora o job. Só faça cache de DataFrames usados mais de uma vez e caros de recalcular, e sempre chame unpersist().

Memória, spill e OutOfMemory

Situação: o job falha com java.lang.OutOfMemoryError ou Container killed by YARN for exceeding memory limits.

Spill

Quando a memória de execução acaba, o Spark grava dados temporários em disco e continua. O job não quebra, mas fica mais lento. No Spark UI aparece como "Spill (Memory)" e "Spill (Disk)".

OOM

Acontece quando algo precisa estar inteiro na memória e não cabe: um collect() grande no Driver, um broadcast grande demais, uma partição gigante por skew, ou o processo Python estourando o overhead.

Como resolver, em ordem

  1. Descubra onde estourou: no Driver ou num executor.
  2. No Driver: remova collect() e toPandas() grandes, reduza o broadcast.
  3. Num executor: aumente o número de partições (partições menores), trate skew, reduza cache.
  4. Com PySpark e UDFs: aumente spark.executor.memoryOverhead.
  5. Só por último aumente executor-memory. Mais memória esconde o problema, não resolve.

UDF Python lenta

Situação: você criou uma função Python com @udf e o job ficou 10 vezes mais lento.

O que acontece

O Spark roda na JVM. Para uma UDF Python, cada linha precisa ser serializada, enviada a um processo Python separado, processada e devolvida. Além disso, o otimizador não consegue enxergar dentro da UDF.

Por que funções nativas ganham

As funções de pyspark.sql.functions rodam dentro da JVM, com geração de código otimizado (Tungsten) e sem atravessar processos. Quase sempre existe uma função nativa para o que você precisa.

# lento: UDF Python linha a linha
@F.udf("string")
def faixa(v): return "alto" if v > 1000 else "baixo"

# rápido: função nativa
df.withColumn("faixa", F.when(F.col("valor") > 1000, "alto").otherwise("baixo"))

# se precisar mesmo de Python: pandas UDF (vetorizada com Apache Arrow, em lotes)
@F.pandas_udf("double")
def com_imposto(v: pd.Series) -> pd.Series: return v * 1.1
Parte 3

Armazenamento e formatos

Metade da performance de um pipeline é decidida em como os dados estão gravados.

Parquet e o formato colunar

Situação: a mesma consulta no Athena lê 100 GB em CSV e 3 GB em Parquet. Por quê?

O que é

Um formato que grava os valores de cada coluna juntos, em blocos (row groups), com metadados de mínimo, máximo e contagem por bloco, além de compressão (Snappy ou ZSTD).

Por que é tão melhor para análise

  • Lê só as colunas usadas (column pruning).
  • Comprime muito mais: valores parecidos lado a lado (a coluna uf repete "SP") compactam bem.
  • Pula blocos usando os metadados: se o máximo de um bloco é 50, um filtro valor > 100 nem o lê.
  • Guarda o schema e os tipos, o que evita erros de parsing.
Na entrevista: "Quando não usar Parquet?"

Para escrita linha a linha e de baixa latência (é um formato de lote, imutável), para leitura de uma linha inteira por chave (use um banco) ou quando precisa ser lido por humanos e ferramentas simples. A camada bronze às vezes fica em JSON, para preservar o dado bruto exatamente como chegou.

Predicate pushdown e partition pruning

Situação: você filtra por data, mas o job lê o bucket inteiro.

Partition pruning

Se a tabela está particionada em pastas (dt=2026-11-10/), um filtro pela coluna de partição faz o Spark ou o Athena nem listarem as outras pastas. É o corte mais barato que existe.

Predicate pushdown

O filtro é "empurrado" para a leitura do arquivo: o leitor Parquet usa os metadados de mínimo e máximo para pular row groups inteiros antes de trazer dados para a memória.

O que quebra o pruning

-- quebra: função aplicada à coluna de partição, o motor não consegue cortar pastas
WHERE date_format(dt, '%Y-%m') = '2026-11'
-- funciona: comparação direta com a coluna
WHERE dt BETWEEN DATE '2026-11-01' AND DATE '2026-11-30'

Também quebra: comparar tipos diferentes (string com data) e filtrar depois de uma UDF. Confirme com explain(): procure PartitionFilters e PushedFilters.

O problema dos arquivos pequenos

Situação: um streaming grava um arquivo de 50 KB por minuto. Depois de um mês, consultar a tabela leva 10 minutos.

Por que é um problema

  • Overhead por arquivo: cada um custa uma listagem e um GET no S3, mais a leitura do rodapé (metadados) do Parquet. O motor passa mais tempo abrindo arquivos do que lendo dados.
  • Tasks demais: cada task tem custo fixo de agendamento; milhares de tasks de milissegundos desperdiçam o cluster e sobrecarregam o Driver.
  • Compressão pior: row groups pequenos comprimem menos e os metadados de mínimo e máximo pulam menos dados.
  • Custo no S3: você paga por requisição, e o S3 limita requisições por prefixo (erro 503 Slow Down).

De onde ele vem

  • Partições demais na escrita: com 200 partições de shuffle (o padrão) e partitionBy("dt") em 30 dias, até 200 × 30 = 6.000 arquivos.
  • partitionBy com alta cardinalidade: por cliente_id, uma pasta com arquivos minúsculos para cada cliente.
  • Streaming com micro-batch curto: um arquivo por partição a cada gatilho.
  • Firehose com buffer pequeno e appends frequentes (de hora em hora).

Como detectar

# quantos arquivos e qual o tamanho total numa partição
aws s3 ls s3://lake/silver/pedidos/dt=2026-11-10/ --recursive --summarize --human-readable

-- no Iceberg, direto por SQL
SELECT COUNT(*) AS arquivos, AVG(file_size_in_bytes) / 1024 / 1024 AS mb_medio
FROM silver.pedidos.files;

Tamanho médio abaixo de 32 MB já justifica compactar. No Spark UI, um stage de leitura com milhares de tasks de poucos milissegundos é o sinal clássico.

Como resolver na escrita: calcular o número de arquivos

ALVO_MB = 256
tamanho_mb = 6 * 1024                                # volume estimado da saída (6 GB)
n_arquivos = max(1, tamanho_mb // ALVO_MB)           # 24 arquivos
df.repartition(n_arquivos).write.mode("overwrite").parquet("s3://lake/silver/x/")

# com partitionBy: reparticione pela mesma coluna, assim cada pasta recebe poucos arquivos
(df.repartition("dt")
   .write.partitionBy("dt")
   .option("maxRecordsPerFile", 5_000_000)            # teto de linhas por arquivo, evita um arquivo gigante
   .parquet("s3://lake/silver/pedidos/"))

# ou deixe o AQE juntar as partições pequenas do shuffle antes de gravar
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "256m")

Como resolver depois: compactação

# Parquet comum: reescreve a partição em poucos arquivos numa pasta nova
p = "s3://lake/silver/pedidos/dt=2026-11-10/"
spark.read.parquet(p).coalesce(8).write.mode("overwrite").parquet(p.rstrip("/") + "_compactado/")
# depois aponte o catálogo para a pasta nova; nunca sobrescreva a pasta que você está lendo

-- Iceberg: troca os arquivos de forma atômica, sem parar as leituras
CALL glue_catalog.system.rewrite_data_files(table => 'silver.pedidos',
     options => map('target-file-size-bytes', '268435456'));
OPTIMIZE silver.pedidos REWRITE DATA USING BIN_PACK;   -- equivalente no Athena

Na leitura (paliativo)

spark.sql.files.maxPartitionBytes (padrão 128 MB) e spark.sql.files.openCostInBytes fazem o Spark agrupar vários arquivos pequenos numa mesma task de leitura. Reduz o número de tasks, mas não as requisições ao S3. É um alívio, não a cura.

Cuidado

  • O oposto também é ruim: um único arquivo de 50 GB tira o paralelismo de quem escreve e de quem lê. Mire em 128 MB a 1 GB.
  • coalesce(1) para "resolver" arquivos pequenos transforma o último stage numa única task.
  • Sobrescrever uma pasta enquanto outro job lê dela causa leituras quebradas. É uma das razões para usar Iceberg.
Na entrevista: "Sua tabela no Athena ficou lenta com o tempo, sem o volume crescer muito. O que é?"

O suspeito principal é o acúmulo de arquivos pequenos (e, no Iceberg, de snapshots e metadados). Confiro a quantidade e o tamanho médio dos arquivos por partição. Resolvo com compactação agendada (rewrite_data_files e expire_snapshots no Iceberg), correção na origem (buffer maior no Firehose, repartition antes de gravar, gatilho de streaming mais longo) e um alarme para o número de arquivos por partição.

Na entrevista: "Por que 200 arquivos por partição se você só tem 1 GB de dados?"

Porque spark.sql.shuffle.partitions é 200 por padrão: depois de um shuffle, cada uma das 200 tasks grava um arquivo em cada pasta de partitionBy em que tem dados. Resolvo com repartition pela coluna de partição antes de gravar, ajustando o número de partições ao volume, ou com o AQE juntando as partições pequenas.

Particionamento vs bucketing

Situação: você particionou por cliente_id e agora tem 2 milhões de pastas.

ParticionamentoBucketing
Como gravaUma pasta por valor (dt=2026-11-10/)Número fixo de arquivos, por hash da coluna
Bom paraColunas de baixa cardinalidade, usadas em filtro (data, região)Colunas de alta cardinalidade usadas em join (cliente_id)
GanhoPula pastas inteiras na leituraEvita shuffle em joins entre tabelas com o mesmo bucketing
Erro comumParticionar por coluna com milhões de valoresNúmero de buckets diferente entre as tabelas do join

Por que o bucketing evita shuffle

Se as duas tabelas foram gravadas com o mesmo hash e o mesmo número de buckets na chave do join, a linha do cliente 42 já está no mesmo número de bucket nas duas. O Spark faz o join bucket a bucket, sem redistribuir nada.

Iceberg e os table formats

Situação: você precisa corrigir 10 linhas antigas numa tabela Parquet de 5 TB, ou apagar os dados de um cliente por LGPD.

O que é

Uma camada de metadados sobre arquivos Parquet que transforma uma pasta do S3 numa tabela de verdade: com transações ACID, UPDATE, DELETE, MERGE, histórico de versões (time travel) e mudança de schema segura. Alternativas: Delta Lake e Hudi.

Por que funciona

Os arquivos Parquet nunca são alterados. Cada escrita cria arquivos novos e um novo snapshot, uma lista de quais arquivos compõem a tabela agora. Leitores sempre veem um snapshot completo, nunca uma escrita pela metade. A troca de snapshot é atômica no catálogo.

MERGE INTO silver.pedidos t
USING atualizacoes s ON t.id = s.id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

SELECT * FROM silver.pedidos FOR TIMESTAMP AS OF TIMESTAMP '2026-11-01 00:00:00';  -- time travel

Cuidado

Muitas escritas pequenas geram muitos snapshots e arquivos. Rode manutenção periódica: compactação, expire_snapshots e remoção de arquivos órfãos.

Parte 4

AWS: problemas reais e o porquê

Cold start na Lambda

Situação: a primeira requisição da API leva 3 segundos e as seguintes, 80 ms.

O que é

Quando não há um ambiente pronto, a AWS precisa criar um: baixar o código, iniciar o runtime e rodar o código fora do handler (imports, clients). Esse é o cold start. Ambientes ficam vivos por alguns minutos e são reaproveitados (warm start).

Como reduzir

  • Pacote menor e menos imports pesados (pandas custa caro).
  • Crie clients fora do handler, para reaproveitar.
  • Mais memória também dá mais CPU, e a inicialização fica mais rápida.
  • Provisioned concurrency: mantém N ambientes sempre quentes (pago).
  • SnapStart (Java e Python): restaura de um snapshot já iniciado.

Visibility timeout no SQS

Situação: a mesma mensagem é processada duas ou três vezes, sem nenhum erro no log.

O que é

Quando um consumidor recebe a mensagem, ela fica invisível para os outros por um tempo. Se o consumidor não a apagar nesse prazo, o SQS assume que ele morreu e torna a mensagem visível de novo.

Por que duplica

Se o processamento leva 60 s e o visibility timeout é 30 s, a mensagem reaparece no meio do trabalho e outro consumidor a pega. Não houve erro: o timeout é que estava curto demais.

Ajuste o visibility timeout para mais que o tempo de processamento (com Lambda, a AWS recomenda 6 vezes o timeout da função) e mantenha o consumidor idempotente, porque o SQS padrão é at-least-once de qualquer forma.

Hot partition no DynamoDB

Situação: a tabela tem capacidade de sobra, mas as escritas recebem ProvisionedThroughputExceededException.

Por que acontece

O DynamoDB divide os dados em partições físicas pelo hash da partition key, e cada partição tem um limite próprio (cerca de 1.000 escritas e 3.000 leituras por segundo). Se a PK é data e todo mundo grava "hoje", tudo cai numa partição só, e as outras ficam ociosas. É o mesmo princípio do skew no Spark.

Como resolver

  • Escolha uma PK com alta cardinalidade e acesso bem distribuído (cliente_id, pedido_id).
  • Write sharding: DATA#2026-11-10#7, com um sufixo de 0 a N, e leia os N shards em paralelo.
  • Evite PKs sequenciais ou de status ("PENDENTE").

Athena cara e lenta

Situação: a fatura do Athena veio alta e uma consulta simples leva minutos.

Por que

O Athena cobra por terabyte lido do S3 (cerca de US$ 5 por TB). Tudo que reduz bytes lidos reduz custo e tempo ao mesmo tempo.

AçãoEfeito típico
CSV/JSON → Parquet com compressãoLê de 5 a 30 vezes menos
Particionar por data e filtrar por elaLê só os dias pedidos
SELECT só das colunas necessárias, nunca SELECT *Lê só essas colunas
Compactar arquivos pequenosMenos tempo de abertura de arquivos
Partition projectionEvita listar milhares de partições no catálogo
Workgroup com limite de bytes por consultaImpede uma consulta acidental de varrer tudo

Lambda esgota as conexões do RDS

Situação: num pico, o Postgres retorna too many connections e a API cai.

Por que acontece

Cada ambiente de Lambda abre a própria conexão. Num pico de 1.000 execuções simultâneas, são 1.000 conexões, mas o Postgres aguenta algumas centenas, e cada conexão consome memória do banco.

Como resolver

  • RDS Proxy: um pool de conexões gerenciado entre a Lambda e o banco, que multiplexa muitas Lambdas em poucas conexões.
  • Limite a concorrência da função (reserved concurrency).
  • Abra a conexão fora do handler, para reaproveitar.
  • Coloque uma fila na frente, para que a escrita aconteça no ritmo que o banco aguenta.
Parte 5

Sistemas distribuídos e bancos

Backpressure

Situação: o produtor gera 10 mil eventos por segundo e o consumidor processa 2 mil.

O que é

Um mecanismo para o consumidor sinalizar "mais devagar" ou para o sistema absorver a diferença sem derrubar ninguém.

Por que filas resolvem

A fila (SQS, Kinesis) funciona como uma caixa d'água: absorve o pico e o consumidor drena no próprio ritmo. A métrica a observar é a idade da mensagem mais antiga: se ela cresce sem parar, o consumidor nunca alcança o produtor e é preciso escalar.

Retry com backoff exponencial e jitter

Situação: uma API caiu por 10 segundos. Quando voltou, mil clientes tentaram ao mesmo tempo e a derrubaram de novo.

O que é

Backoff exponencial: esperar 1 s, 2 s, 4 s, 8 s entre tentativas. Jitter: somar um tempo aleatório a cada espera.

Por que o jitter importa

Sem jitter, todos os clientes que falharam juntos tentam de novo juntos, em ondas sincronizadas que derrubam o serviço outra vez (thundering herd). O aleatório espalha as tentativas no tempo.

import random, time
def com_retry(fn, tentativas=5, base=0.5, teto=20):
    for i in range(tentativas):
        try:
            return fn()
        except ErroTemporario:
            if i == tentativas - 1:
                raise
            time.sleep(random.uniform(0, min(teto, base * 2 ** i)))   # "full jitter"

Só refaça o que é seguro repetir (operações idempotentes) e só para erros temporários (timeout, 429, 503), nunca para 400.

Índices no banco relacional

Situação: SELECT * FROM pedidos WHERE cliente_id = 42 leva 8 segundos numa tabela de 50 milhões de linhas.

O que é

Uma estrutura à parte (normalmente uma B-tree) que guarda os valores da coluna em ordem, com ponteiros para as linhas. É como o índice remissivo de um livro.

Por que é rápido

Sem índice, o banco lê as 50 milhões de linhas (seq scan). Com a B-tree, encontra o valor em poucos saltos (busca logarítmica): cerca de 4 ou 5 leituras de página em vez de milhões.

EXPLAIN ANALYZE SELECT * FROM pedidos WHERE cliente_id = 42;   -- Seq Scan: problema
CREATE INDEX CONCURRENTLY idx_pedidos_cliente ON pedidos (cliente_id, criado_em DESC);
-- índice composto: atende o filtro por cliente e já entrega ordenado por data

Cuidado

  • Todo índice deixa a escrita mais lenta e ocupa espaço. Não indexe tudo.
  • A ordem das colunas no índice composto importa: (cliente_id, criado_em) serve para filtro só por cliente_id, mas não só por criado_em.
  • Uma função na coluna (WHERE lower(email) = ...) ignora o índice comum; crie um índice de expressão.
  • CONCURRENTLY evita travar a tabela em produção.
Parte 6

Treino: dicas, simulado e casos

Leia as dicas, faça o simulado sem consultar as fichas e depois tente os casos abertos em voz alta.

Dicas para a entrevista técnica

Responda em 3 camadas

1) o que é, numa frase; 2) por que funciona; 3) quando não usar. Exemplo: "Broadcast join copia a tabela pequena para cada executor. Funciona porque evita o shuffle da tabela grande. Não serve quando a tabela pequena passa de algumas centenas de MB."

Comece pelo diagnóstico

Em "meu job está lento", nunca pule direto para a solução. Diga primeiro como mediria: Spark UI (qual stage, duração das tasks, shuffle, spill) e explain(). Quem mede antes de mexer passa senioridade.

Fale de trade-off

Toda escolha tem custo. "coalesce é mais barato, mas reduz o paralelismo." "Cache acelera, mas tira memória do shuffle." Mostrar o lado ruim é o que separa decorar de entender.

Use números

Partições de 128 a 256 MB; broadcast até dezenas ou poucas centenas de MB; shuffle.partitions padrão 200; Lambda até 15 min; Athena cerca de US$ 5 por TB lido. Números dão credibilidade.

Tenha uma história real

Casos abertos (estilo entrevista de arquitetura)

Não há alternativas. Responda em voz alta por 2 ou 3 minutos e só depois abra a resposta-modelo.

1. Um job Glue que levava 20 minutos passou a levar 3 horas, sem mudança de código.

Investigação: comparar o volume de entrada (cresceu?), o número e tamanho dos arquivos (acumulou arquivos pequenos?), e no Spark UI ver qual stage ficou lento e se há skew (uma task muito maior) ou spill. Causas prováveis: uma chave que ficou quente, arquivos pequenos na origem, um lado do join que cresceu e deixou de caber no broadcast automático. Ações: AQE com skew join, compactação, broadcast explícito ou salting, mais DPUs só por último. Prevenção: alarme de duração do job e métrica de arquivos por partição.

2. Desenhe a ingestão de 50 mil eventos por segundo de um app até o data lake, consultável em até 5 minutos.

App → API Gateway ou ALB → serviço no ECS que valida e publica no Kinesis Data Streams (alto volume, ordem por chave, replay). Kinesis → Firehose com buffer de 128 MB ou 300 s, conversão para Parquet e particionamento dinâmico por data → S3 bronze. Um job (Glue streaming ou EMR) faz MERGE numa tabela Iceberg silver, e uma compactação horária resolve os arquivos pequenos. Athena consulta. Observabilidade: idade do iterador do Kinesis, falhas do Firehose para um bucket de erro e alarmes. Por que Kinesis e não SQS: volume alto, vários consumidores e possibilidade de reprocessar.

3. O time de produto quer um endpoint que devolva "total gasto pelo cliente nos últimos 12 meses" em menos de 100 ms.

Não consultar o data lake na hora: Athena e Spark não têm latência de milissegundos. Pré-calcular o agregado num job (diário ou incremental por eventos) e gravar num armazenamento de leitura rápida por chave, como o DynamoDB (PK = cliente). A API (Lambda ou ECS) lê por chave. Se precisar ser quase em tempo real, um consumidor de eventos atualiza o total a cada pedido com update atômico. Trade-off: dado levemente defasado em troca de latência e custo previsíveis.

4. Um consumidor de fila está cobrando clientes duas vezes.

A fila é at-least-once e o consumidor não é idempotente; ou o visibility timeout é menor que o tempo de processamento, e a mensagem reaparece. Correção: chave de idempotência (id do evento) gravada com escrita condicional no DynamoDB antes de cobrar, com status de processamento; ajustar o visibility timeout; usar a idempotency key também na chamada ao gateway de pagamento. Depois: reconciliar as cobranças duplicadas e criar alarme.

5. Você precisa apagar todos os dados de um cliente do data lake por pedido de LGPD.

Em Parquet puro, seria preciso reescrever todos os arquivos que contêm o cliente. Com Iceberg: DELETE FROM tabela WHERE cliente_id = X em cada camada, depois expire_snapshots e remoção de arquivos órfãos, para que o dado saia também do histórico. Na bronze imutável, pseudonimizar o dado pessoal na entrada (token no lugar do CPF, com o mapeamento numa tabela à parte) facilita: basta apagar o mapeamento. Registrar a execução para auditoria.

6. Sua API no ECS fica lenta todo dia às 9h.

Ver as métricas por horário: CPU e memória das tasks, latência p99, conexões com o banco, tempo das queries. Prováveis causas: auto scaling reagindo tarde (escala por CPU demora), banco saturado de conexões ou com queries sem índice, cold start de dependências. Ações: scheduled scaling antes das 9h, scaling por número de requisições no ALB, pool de conexões ou RDS Proxy, índices, cache para leituras repetidas. Confirmar com tracing (X-Ray) onde o tempo é gasto.
